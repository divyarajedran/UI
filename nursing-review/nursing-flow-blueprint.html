Nursing Flow Blueprint

How nursing works today in the web HMS (Healthcare Management System) and in the Flutter DoctorApp, what reaches the doctor and what doesn't, and a design for a floor-locked, QR-scan nursing flow in the mobile app.

Summary

Summary: a nursing module exists, but floor access isn't enforced

The web app has a large Nursing Automation module with 45 API actions: OP nurse queue, task board, medication administration, ward workspace, duty roster, handover and reports. Real usage is low (for example, 110 nursing tasks and 7 OP queue rows in the audit). Floor and ward allocation is only a UI default. The server doesn't enforce it, and there's no bed QR code.

WorksIP vitals, nursing notes and I/O reach the doctor

They are shared tables, visible on the IP timeline, the case sheet and the IP EMR in both web and app.

PartlyMedicines given are visible, but only in the nurse console

Doctors see the MAR only when they open the shared nurse_console page. It isn't on the timeline or the doctor workspace.

DoubtfulOP queue vitals probably don't reach the doctor's case sheet

The OP queue writes vitals_monitoring, but the case sheet reads the visit-report path. Needs a DB check.

MissingFloor-locked access and bed QR scanning

Roster floor/ward data exists, but no screen or API blocks a nurse from other floors. There's no bed QR (the only QR is the food-ordering one).

SplitIP nutrition data sits in the external MOP F&B service

Diet orders live in HMS, but consumption %, calories and protein are stored only in MOP. The doctor never sees them.

PartlyNurses see medicine orders, but not the doctor's full summary

Prescriptions are visible in the nurse console. Doctor notes, investigations and instructions require opening the EMR timeline.

Exists & wiredPartial / split / buggyMissing or not wiredInferred (SP body not in repo)

This is the full lifecycle, from admission to discharge. Each step shows its status, and green means data lands in tables the doctor timeline reads.

Admission request

The doctor fills in instructionToNurse. It's only visible again if the admit form is reopened.

8 slots (FBS, PPBS, RBS, pre/post meals, 3 AM).

Nursing notes

Tasks board

NurseConsolePro and Worklist. Overdue auto-escalation and order-triggered tasks aren't wired, and photo/vitals completion isn't captured.

Diet

Shift end and exit

Shift handover

Save only: per-patient notes are lost ([object Object]), nurse ids are 0, and there's no read or acknowledge screen.

Bed transfer

Transfer order generates transfer tasks.

Discharge

Workflow 'FD' step generates discharge tasks. The summary uses admission vitals only.

Care plan, Braden/Morse, IP fall risk

Missing. The ICU nursing assessment page is static HTML and can't save.

What nurses can see of doctor orders

  • Yes Medicine orders (dose, frequency, taper, instructions, doctor name, allergy check) in nurse_console
  • Yes Diagnosis and last vitals on worklist and ward cards
  • Hidden Doctor notes, investigations and instructions: the nurse must open the EMR timeline
  • No Lab/investigation orders as nursing tasks (GENERATE_ORDER is never called)
  • No Flutter nurse app can't open prescriptions or the EMR. It only has medication rows and the "assigned by doctor" name.

What this means for mobile

  • Write vitals to Vitalsmonitoring, and write MAR through the nurse_console administer path. That's the path the doctor reads, and it also copies vitals.
  • Don't use the automation MedicationDeliveryUpdate path (the one the app uses today). Its status vocabulary differs and nothing mirrors it to the doctor.
  • Add a "Nursing" tab to the doctor's IP patient screen showing MAR, tasks, diet and handover.
Nutrition

Nutrition and diet: three separate systems

OP · doctor

Diet & exercise plan

diet_excercise: goal duration, kcal, food type, servings, instructions. Plus nutritional screening flags (appetite, weight loss) and "observed nutrition".

IP · V2

IP Diet V2 (current)

IpDietPrescription: diet type, texture, portion, meal timings, instructions. Orders go to MOP F&B. Consumption %, taste, calories, protein and nutritional risk are stored only in MOP.

IP · legacy

Diet delivery tracking

diet_delivery_tracking has 0 rows because its generator has no caller. The DietDelivery page and the Flutter Diet tab read this table, so both are always empty.

Recommendation: mobile shows the V2 diet order (read) and records consumption to MOP and to a local HMS mirror, so the doctor view can show "Ate 50% of lunch · 1,150 of 1,800 kcal today".

Gaps

Gaps to fix before (or while) building mobile

  1. No server-side access control by location. Any nurse can read and write any patient. The mobile QR lock must be enforced by the API, not by the app.
  2. Nurse identity is lost on writes. nurse_id comes from the DoctorId cookie, which is null for nurses. Every mobile write needs nurse_user_id taken from the token.
  3. Two MAR status vocabularies and two write paths. Standardize on the nurse_console path.
  4. OP queue vitals don't reach the case sheet (inferred). Confirm in the DB, then have SP_OPVitalsEntry_NurseQueue also write the visit-report vitals.
  5. Handover is broken, and overdue/escalation jobs aren't wired. Fix the save, add acknowledgement, and schedule CHECK_OVERDUE.
  6. Diet consumption exists only in MOP. Mirror it into HMS so doctors and reports can see it.
  7. Display board API is public. It has no [Authorize] and returns patient names, beds and vitals.
Proposal · Flutter nursing flow

Mobile nursing flow: floor-locked QR access

Scenario (example data). Staff Nurse Priya is rostered on the Morning shift (06:00–14:00) for 3rd and 4th floor. Every bed has a printed QR label.

DeniedScans 2F · Ward A · Bed 01

"Access denied: this bed is on 2nd floor. You're allotted 3F and 4F this shift." The scan is logged. The nurse can request temporary cover from the charge nurse.

AllowedScans 3F · Ward B · Bed 07

The patient chart opens with name, UHID, age, allergies and diagnosis, with tabs for Vitals, Meds due, MAR, I/O, Nutrition, Notes, Tasks and Doctor summary.

Round tripDoctor sees it immediately

Vitals, MAR, notes and I/O go into the same tables the doctor reads. Diet consumption is mirrored. The doctor's IP screen gains a Nursing tab.

How the access check works (server-side)

InputApp sends POST /api/NurseMobile/ScanBed with the QR token and a bearer JWT
↓ decode token → bed_id (verify HMAC)
Resolve bed → ward → floorbed_managemet_details → ward_management_details.floorid
↓ nurse_user_id from JWT, never from the request body
Is there an active roster row for this nurse now, covering this floor or ward?nursing_duty_roster: duty_date or standing range, shift window, floorid/wardid/current_wardid, PUBLISHED. Plus approved temporary cover.
No → 403Returns the reason, the nurse's allotted floors and the charge nurse on that floor. Logs DENIED.
Yes → 200Returns the patient on that bed (visit_reportid) and a short-lived bed-access grant (valid until shift end). Logs GRANTED.
↓ every write carries the grant
Every write API re-checks the grant against visit_reportidThis stops someone from calling the vitals or MAR API for a 2F patient directly.

Design decisions

  • QR payload: HMSBED:v1:{bedId}:{hmac}. Contains no patient data, so a label on the wall reveals nothing. The label is reprinted only when the bed id changes.
  • The bed QR stays fixed while patients change: the server looks up the current occupant at scan time, so transfers and discharges need no relabelling.
  • Empty bed: "Bed 07 is vacant". Transferred patient: "Patient moved to 4F-12", which opens only if 4F is allotted.
  • Floor list is also the home screen: nurses can browse their floors' census without scanning, but writes on the MAR step require a scan (a bedside check).
  • Charge nurse / NS: a role flag gives read-all access. Writes still follow the roster, or use an explicit "cover" assignment.
  • Shift end: grants expire, and the app prompts for the handover.
  • Offline: vitals and notes queue locally with their timestamp. MAR writes must be online (to prevent double dosing).
  • Phase 2: add a patient wristband scan and a medicine barcode check (right patient, right drug).
